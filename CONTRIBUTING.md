# Contributing

Thanks for taking a look. This is a benchmark harness with a deliberately narrow scope. Small,
well-tested changes that keep measurements honest are the most useful kind.

## Before you open a pull request

1. `bash scripts/setup.sh`, then `bash scripts/smoke.sh`.
2. Run the checks that match your change ([docs/development.md](docs/development.md)). For most
   changes that means:
   ```sh
   export PYTHONPATH="$PWD/analysis/src" MPLBACKEND=Agg PYTHONDONTWRITEBYTECODE=1 PHASE1_FRAMEWORKS=none
   swift build --disable-keychain
   bash scripts/swift_test.sh --disable-keychain
   .venv/bin/python -m pytest analysis/tests -q
   ```
3. In the PR, say which checks you ran, on which macOS, chip and toolchain, and which you could not run.

## Ground rules

- **Frozen contracts.** Schema v1, metric and normalizer definitions, and the event vocabulary are
  frozen. A change needs a new versioned policy or schema plus tests, not an in-place edit.
- **Never overwrite evidence.** Scripts and the CLI refuse existing outputs. Keep it that way.
- **Mocks are not models.** Mock and stub-model tests prove harness and wrapper behavior. Do not
  describe them as recognition results.
- **Claims need evidence.** Do not add numbers or capability claims (throughput, latency,
  accelerator use, power, accuracy rankings) unless measurements and caveats back them
  ([docs/benchmarking.md](docs/benchmarking.md)).
- **Default lock.** Commit `Package.resolved` only for the default graph. Build optional SDK graphs
  in a separate checkout.
- **No private data.** Never commit or attach recordings, model weights, datasets, inputs files,
  credentials or full run directories, whether in a PR or an issue. Synthetic fixtures are
  generated by `scripts/generate_fixtures.py`.
- New adapters follow [docs/phase1-adapter-guide.md](docs/phase1-adapter-guide.md).
